## 1. What the manifest pins

[`atlas-1.0.0-rc.1.json`](atlas-1.0.0-rc.1.json) records the committed content of the
candidate. Everything is read through git (`git ls-files -s` and `git cat-file`), not from the
files on disk, so line-ending conversion at checkout does not affect it. It records:

- **source**: the mode and the SHA-256 of the committed content of every tracked file except
  the manifest itself, a tree fingerprint over them, and one fingerprint per area (package,
  tests, dashboard sources and build, deployment, configurations, snapshot, research results,
  contract, CI, legacy artifacts);
- **dependency locks**: `uv.lock`, `pyproject.toml`, `.python-version`,
  `web/package-lock.json`, `web/package.json`, `web/.npmrc` and the hash-pinned uv bootstrap
  `.github/ci-requirements.txt`;
- **toolchain and environment requirements**: Python 3.12 (uv 0.11.32), Node.js only to build
  and test the dashboard, and the server requirements;
- **snapshot provenance**: `legacy-v0`, its manifest hash, the data fingerprint, the source, the
  window, and the recorded gaps (extraction time unknown, terms of use unverified). The data
  fingerprint is the one that the M2, M3 and M4 results share; the tool refuses to write or
  check a manifest when they disagree, or when a run names another snapshot manifest;
- **research artifacts**: every committed run under `docs/results/`, with its manifest hash,
  run id, record type, configuration and result fingerprints, and every output file's hash;
- **build artifacts**: the committed dashboard build `web/dist` (every file, and its own
  manifest);
- **API contract**: `docs/api/openapi.json`, its hash, `info.version` and operation count;
- **scientific status**, in two parts:
  - what the committed results record: the M2 recommendation and primary tests (H1 not
    significant after Holm); the archived M2 projection (origin, last data date, target dates);
    `failed_calibration` for M3; `HYPOTHETICAL` provenance in every one of the 33 provenance
    declarations of the M4 configuration (16 base quantities, 11 scenario adjustments,
    6 sensitivity sweeps); and the M4 manifest's `validated_recommendation: false`;
  - what the release declares: the weak selection evidence of the M8 erratum, that the
    projection has never been scored, `validated_recommendation: false`, and the candidate's
    own status.

The manifest also names the commit it was generated from, for information only: the content
identifies the candidate. A server release adds its own `release.json` at build time (the exact
commit, the installed wheels and the environment fingerprint on that machine;
[DEPLOYMENT.md](../DEPLOYMENT.md) section 10).

## 2. Verify a checkout against the candidate

```bash
git clone https://github.com/arthur-fay/demand-forecasting-model.git atlas && cd atlas
git checkout <candidate commit>
python3 docs/release/rc_manifest.py --check        # Python 3.11 or later and git; standard library only
```

How `--check` works:

1. **Clean checkout.** `git status` must list nothing apart from the manifest. Otherwise the
   tool names the paths (the first 50, then the total) and exits 1. Ignored files such as
   `.venv` are neither checked nor refused, so verify in a fresh clone.
2. **Comparison.** It recomputes the manifest from the content git has committed and compares
   the two:
   - exit 0 prints the tree fingerprint and the number of files it covers. Compare it with the
     fingerprint published for the candidate in the pull request (and in the annotation of its
     tag). It cannot be written into the repository, because every tracked file but the
     manifest is part of it.
   - exit 1 names the added, removed or changed files and the mode changes (the first 50, then
     the total).
   - exit 2 means the tool could not run: for example no git, Python older than 3.11, or
     committed results that disagree on the data fingerprint.

A checkout made with `core.autocrlf=true`, the Git for Windows default, verifies like any
other. A shallow clone is enough.

The manifest is generated last, in a clean checkout of the final tree, and committed alone:
`--write`, then `--check` (which notes that the manifest is not yet committed), then the
commit, then `--check` in a fresh clone. **Any later change to the content makes the check
fail**, so a change after the manifest means regenerating it, and a change after approval means
a new candidate (section 4).

## 3. Reproducible build and verification

Requirements:

- Linux x86-64 (x86-64-v2) or aarch64;
- Python 3.12;
- uv 0.11.32 (CI installs it from the hash-pinned `.github/ci-requirements.txt`);
- Node.js 22.22.2 or later in the 22 line, only for the dashboard checks;
- for the deployment tests: nginx, openssl, shellcheck and systemd-analyze on `PATH`, plus
  Docker for the container test.

Byte-identical results have two further conditions:

- **CPU class.** The research runs that involve the regression (M2, M3 and the legacy holdout)
  reproduce byte for byte only on the CPU class of the reference runs. There, the locked
  NumPy's OpenBLAS uses its SkylakeX (AVX-512) kernels;
  `OPENBLAS_VERBOSE=2 uv run python -c "import numpy"` prints the core in use. On other CPUs
  their `verify` reports last-bit differences, and the tests compare within 1e-9 instead
  ([DEVELOPMENT.md](../DEVELOPMENT.md), reproduction). The M4 run did not depend on the kernels
  in the audit: it also reproduced with OpenBLAS's AVX2 (Haswell) kernels.
- **Line endings.** The dashboard build reproduces byte for byte from a checkout with LF line
  endings. On Windows, clone with `git clone -c core.autocrlf=false`, because the build's HTML
  entry file, `web/index.html`, is otherwise converted. The result files, the build and the
  fixtures are protected by `.gitattributes` whatever the setting. The manifest check
  (section 2) compares committed content, so it is not affected either.

These are the checks CI runs (`.github/workflows/ci.yml`), job by job:

```bash
# quality: the locked environment, static checks, tests and the reference data
python -m pip install --require-hashes -r .github/ci-requirements.txt
uv sync --locked
uv run ruff format --check . && uv run ruff check . && uv run mypy
ATLAS_REQUIRE_DEPLOY_TOOLS=1 uv run pytest          # needs nginx, openssl, shellcheck, systemd-analyze
shellcheck --severity=style deploy/scripts/*.sh
uv run atlas check && uv run atlas quality && uv run atlas backtest legacy
uv run atlas backtest run --config configs/backtest/smoke.json --output-dir /tmp/m2-smoke
uv run atlas backtest verify /tmp/m2-smoke
uv run atlas uncertainty run --config configs/uncertainty/smoke.json --output-dir /tmp/m3-smoke
uv run atlas uncertainty verify /tmp/m3-smoke
uv run atlas optimize run --config configs/optimization/smoke.json --output-dir /tmp/m4-smoke
uv run atlas optimize verify /tmp/m4-smoke && uv run atlas optimize inspect /tmp/m4-smoke
uv run atlas optimize verify docs/results/atlas-m4-optimization-v1   # byte for byte
uv run atlas optimize inspect docs/results/atlas-m4-optimization-v1
uv run atlas api openapi | diff - docs/api/openapi.json
# (CI then starts `uv run atlas api serve` and requests /health/ready, /api/v1/scenarios and
#  one simulation)

# deploy-e2e: the deployment package end to end in a disposable Ubuntu 24.04 systemd container
uv run pytest tests/test_m6_container.py --no-cov

# dashboard: the committed build is reproduced byte for byte from the lock
cd web && npm ci && npm audit --audit-level=high
npm run format:check && npm run lint && npm run typecheck
npm run gen:api && git diff --exit-code -- src/api/openapi.gen.ts
npm run test:coverage
npm run build && git diff --exit-code -- dist && npm run verify:dist && npm run size
npx playwright install chromium && npx playwright test              # needs nginx and openssl
npx playwright install firefox webkit
ATLAS_E2E_ALL_BROWSERS=1 ATLAS_E2E_API_ONLY=1 npx playwright test --project firefox --project webkit
```

Two further checks are not on every pull request:

- the full research reproduction. It is slow (about 7 and 5 CPU-minutes), and it is also a
  manual CI workflow, `reproduce-research.yml` ([DEVELOPMENT.md](../DEVELOPMENT.md));
- the dependency audit. It runs weekly, and on every pull request that changes a lock
  (`dependency-audit.yml`).

```bash
uv run atlas backtest verify docs/results/atlas-m2-rolling-origin-v1/full        # SkylakeX core
uv run atlas uncertainty verify docs/results/atlas-m3-intervals-v1/full          # SkylakeX core
```

## 4. Versioning policy

The code carries the version being released: `1.0.0` in `pyproject.toml`, `atlas.__version__`,
`web/package.json`, the dashboard build and the API contract (a test keeps them equal). The
deployment tooling accepts `MAJOR.MINOR.PATCH` only, and a release id is
`<version>-<12 hex of the commit>`, so two candidates of the same version are still distinct
releases. Candidate status lives outside the code: in this document, in the manifest's
`candidate` field and in a tag `v1.0.0-rc.1` that **only the owner creates, after approval**. If
the review requires changes, the next candidate is `1.0.0-rc.2` with a regenerated manifest. The
final release is tagged `v1.0.0` on the approved commit.

## 5. Deployment and rollback

Deployment is phase B of M6 and needs the owner's written authorisation:
[VPS_PHASE_B_RUNBOOK.md](VPS_PHASE_B_RUNBOOK.md). On a server, an activation that fails
verification returns automatically to the last verified release and configuration;
`atlas-deploy rollback [--to <release id>]` and `atlas-deploy recover` do so explicitly, and both
re-render the restored release's nginx site, so the dashboard and the API always come from the
same release ([DEPLOYMENT.md](../DEPLOYMENT.md) section 11).

In the repository, rolling back the candidate means not merging it (or reverting its merge
commit); no research result or snapshot file is changed by M8, so nothing else needs restoring.

## 6. Acceptance checklist (for the owner)

Before approving:

- [ ] Read the verdict and the acceptance matrix ([RELEASE_GATE.md](RELEASE_GATE.md)), including
  every gate that is FAIL or NOT VERIFIED.
- [ ] Accept the disclosed limitations ([../KNOWN_LIMITATIONS.md](../KNOWN_LIMITATIONS.md)), and
  say so in the approval of the pull request (or later in the tag's annotation).
- [ ] CI is green on the pull request's head commit (all jobs, including `deploy-e2e`, the
  Firefox and WebKit step and the dependency audit).
- [ ] `python3 docs/release/rc_manifest.py --check` passes on the commit to approve.
- [ ] **The repository is already public.** Decide the project licence (none is included), or
  record that none is granted, and confirm that the NYC Open Data terms permit redistributing
  the committed derived tables with the attribution in the data card. Alternatively, make the
  repository private until both are decided. This must be done before tagging
  ([RELEASE_GATE.md](RELEASE_GATE.md) section 1, condition 3).

Merging and tagging:

- [ ] Approve and merge the pull request (a merge commit keeps the candidate commit reachable).
- [ ] Tag `v1.0.0-rc.1` on the approved commit (owner only).

Before tagging `v1.0.0`:

- [ ] Dispatch `reproduce-research.yml` on the merge commit, and record the date, the commit,
  the CPU, the OpenBLAS core and the outcome ([DEVELOPMENT.md](../DEVELOPMENT.md)).
- [ ] Confirm that `dependency-audit.yml` is enabled, and run it once by hand; it must be green.
- [ ] Tag `v1.0.0` on the same commit (owner only). Any change to the content makes a new
  candidate, `1.0.0-rc.2`, with a regenerated manifest.

Deployment:

- [ ] Authorise or defer M6 phase B (the runbook's section 1 decisions).
