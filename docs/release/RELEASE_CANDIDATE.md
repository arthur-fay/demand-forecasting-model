## 1. What the manifest pins

[`atlas-1.0.0-rc.1.json`](atlas-1.0.0-rc.1.json) records:

- **source**: a SHA-256 fingerprint of every tracked file (and one per area: package, tests,
  dashboard sources and build, deployment, configurations, snapshot, research results, contract,
  CI, legacy artifacts);
- **dependency locks**: `uv.lock`, `pyproject.toml`, `.python-version`, `web/package-lock.json`,
  `web/package.json`, `web/.npmrc` and the hash-pinned uv bootstrap `.github/ci-requirements.txt`;
- **toolchain and environment requirements**: Python 3.12 (uv 0.11.32), Node.js only to build and
  test the dashboard, and the server requirements;
- **snapshot provenance**: `legacy-v0`, its manifest hash, the data fingerprint, the source, the
  window, and the recorded gaps (extraction time unknown, terms of use unverified);
- **research artifacts**: every committed run under `docs/results/` with its manifest hash, run id,
  record type, configuration and result fingerprints, and every output file's hash;
- **build artifacts**: the committed dashboard build `web/dist` (every file, and its own manifest);
- **API contract**: `docs/api/openapi.json`, its hash, `info.version` and operation count;
- **scientific status**: the M2 primary tests (H1 not significant after Holm), the weak selection
  evidence (M8 erratum), `failed_calibration` for M3, `HYPOTHETICAL` for M4, the archived
  projection, `validated_recommendation: false`.

A server release adds its own `release.json` at build time (the exact commit, the installed wheels
and the environment fingerprint on that machine; [DEPLOYMENT.md](../DEPLOYMENT.md) section 10).

## 3. Reproducible build and verification

Requirements: Linux x86-64 (x86-64-v2) or aarch64, Python 3.12, uv 0.11.32 (CI installs it from
the hash-pinned `.github/ci-requirements.txt`), Node.js 22.22.2 or later in the 22 line (only for
the dashboard checks). On Windows, keep the repository's `.gitattributes` (it stops line-ending
conversion of every hash-checked file).

```bash
# Python: the locked environment and every check CI runs
python -m pip install --require-hashes -r .github/ci-requirements.txt
uv sync --locked
uv run ruff format --check . && uv run ruff check . && uv run mypy
ATLAS_REQUIRE_DEPLOY_TOOLS=1 uv run pytest                     # needs nginx, shellcheck, openssl
uv run atlas check && uv run atlas quality && uv run atlas backtest legacy
uv run atlas optimize verify docs/results/atlas-m4-optimization-v1   # byte for byte
uv run atlas api openapi | diff - docs/api/openapi.json

# The full research reproduction (slow; also a manual CI workflow, see DEVELOPMENT.md)
uv run atlas backtest verify docs/results/atlas-m2-rolling-origin-v1/full
uv run atlas uncertainty verify docs/results/atlas-m3-intervals-v1/full

# Dashboard: the committed build must be reproduced byte for byte from the lock
cd web && npm ci && npm audit --audit-level=high
npm run format:check && npm run lint && npm run typecheck && npm run test:coverage
npm run build && git diff --exit-code -- dist && npm run verify:dist && npm run size
npx playwright test                                            # needs nginx and openssl

# The deployment package end to end in a disposable Ubuntu 24.04 systemd container
cd .. && ATLAS_E2E_CONTAINER=1 uv run pytest tests/test_m6_container.py --no-cov
```

## 4. Versioning policy

The code carries the version being released: `1.0.0` in `pyproject.toml`, `atlas.__version__`,
`web/package.json`, the dashboard build and the API contract (a test keeps them equal). The
deployment tooling accepts `MAJOR.MINOR.PATCH` only, and a release id is
`<version>-<12 hex of the commit>`, so two candidates of the same version are still distinct
releases. Candidate status lives outside the code: in this document, in the manifest's
`candidate` field and in a tag `v1.0.0-rc.1` that **only the owner creates, after approval**. If
the review requires changes, the next candidate is `1.0.0-rc.2` with a regenerated manifest. The
final release is tagged `v1.0.0` on the approved commit.

## 5. Deployment and rollback

Deployment is phase B of M6 and needs the owner's written authorisation:
[VPS_PHASE_B_RUNBOOK.md](VPS_PHASE_B_RUNBOOK.md). On a server, an activation that fails
verification returns automatically to the last verified release and configuration;
`atlas-deploy rollback [--to <release id>]` and `atlas-deploy recover` do so explicitly, and both
re-render the restored release's nginx site, so the dashboard and the API always come from the
same release ([DEPLOYMENT.md](../DEPLOYMENT.md) section 11).

In the repository, rolling back the candidate means not merging it (or reverting its merge
commit); no research result or snapshot file is changed by M8, so nothing else needs restoring.
