## 1. What 1.1.0 means

ATLAS **1.1.0** is the release of the M0-M9 content: the 1.0.0 research demonstration of M0-M8,
with every research result unchanged, plus the M9 static, read-only demonstration profile
(prepared and tested, **not published**), the MIT License for original ATLAS code, and the
release records. It is a minor version because it adds a backward-compatible capability: the
static export command and the static build profile. The HTTP API contract is unchanged except
its `info.version`, and nothing that 1.0.0 offered is removed.

1.1.0 is **not** a new scientific result, a new validation, a new data snapshot, a publication
of the website or a deployment. Every scientific result and status of 1.0.0, as corrected by its
M8 erratum, is unchanged:

- **M2: the forecast's advantage over simple baselines is not robustly established.** The
  selected regression's lead over the best simple baseline B\* is not significant after Holm
  (adjusted p 0.054, 95 % interval of the MAE difference −256 to +2 requests per day).
- **The M8 statistical erratum remains valid.** The pre-registered selection test over-rejects
  at a 30-day horizon; after a size correction its p-value is 0.069, above the 5 % gate, so a
  correctly sized test would most likely have kept B\*. The regression is the recommended
  model only under the pre-registered rule as computed
  ([BACKTESTING.md](../BACKTESTING.md) section 12).
- **M3: FAILED_CALIBRATION.** The prediction intervals and exceedance probabilities are **not
  validated for operational use**; none is decision-grade ([UNCERTAINTY.md](../UNCERTAINTY.md)).
- **M4: every staffing, cost, productivity and budget assumption is HYPOTHETICAL.** Its plans
  are optimal only for an invented model, and six of the nine reference scenarios have no plan
  that meets every hypothetical constraint ([OPTIMIZATION.md](../OPTIMIZATION.md)).
- **Archived, not current.** The forecasts are an archived projection issued from data ending
  2026-06-30; they are not current predictions and have never been scored.
- **Independent research software.** ATLAS is not an official or operational NYC tool, and is
  not affiliated with, sponsored or endorsed by the City of New York, NYC 311 or NYC Open Data.

No validation claim is added: 1.1.0 has no new scientific evidence.

## 4. What the manifest pins

[`atlas-1.1.0-rc.1.json`](atlas-1.1.0-rc.1.json) is computed from the content git has committed
(`git ls-files -s`, `git cat-file`), never from the files on disk. It records everything the
1.0.0-rc.1 manifest records ([RELEASE_CANDIDATE.md](RELEASE_CANDIDATE.md) section 1: every
tracked file's mode and SHA-256 with a tree fingerprint and one fingerprint per area, the
locks, the toolchain, the snapshot's provenance and data fingerprint, every research run, the
dashboard build, the API contract and the scientific status), and schema 2 adds:

- **`versions`**: every declaration of the version, twelve in all (the three made by hand, the
  two locks' three entries, the dashboard build, the API contract, the static export's manifest,
  every `atlas_version` of every recorded answer, the static site's manifest and every
  dashboard fixture). The tool refuses to write or check a manifest when any differs from
  `pyproject.toml`'s. (The built JavaScript also contains the version; `verify:dist` and the
  manifests' file hashes tie it to the build manifest's.)
- **`static_site`**: the static export (its manifest's SHA-256, every answer's, the snapshot and
  the scientific status it records), the static site's manifest (its SHA-256, base path, policy
  and file count) and the publication record (its SHA-256 and every condition, as committed;
  `every_condition_true` is true only when the record states exactly the publication gate's
  eight conditions, each of them true; even then the gate also requires the record's version
  and decision fields, the repository switch and a dispatch, so it is not a verdict on
  publication).
  The tool refuses an export manifest that does not list exactly the committed answers, and a
  site manifest built from another export;
- **`candidates`**: the earlier candidates' manifests committed beside it, here
  `atlas-1.0.0-rc.1.json`, by SHA-256, schema, commit and tree fingerprint;
- **more areas**: `docs/release`, `web/static-export`, `web/build` and `web/scripts`;
- **its own documents**: `release_gate` and `release_candidate` are named after the version
  (`RELEASE_GATE_1.1.0.md`, `RELEASE_CANDIDATE_1.1.0.md`), so the manifest never points at the
  M8 documents; it also names the static demo, the code and data terms, the NYC 311 review and
  the publication record;
- **more declared status**: besides the M8 declarations (weak selection evidence, an archived
  projection never scored, `validated_recommendation: false`), the M2 advantage not
  established, M3 `FAILED_CALIBRATION` (intervals not validated for operational use), every M4
  parameter `HYPOTHETICAL`, and independent research software, not an official NYC tool; and
  the candidate's own status: "not released, not tagged, not deployed, not published". The
  declarations are fixed text, so the tool checks them against the results it records and
  refuses a candidate whose results contradict one: H1 significant after Holm at the
  protocol's level (`selection.alpha` of the M2 run), intervals not `failed_calibration` or
  decision-grade, an M4 provenance other than `HYPOTHETICAL`, or a validated M4 recommendation.

The tool writes only the manifest named after the committed version
(`atlas-<version>-rc.1.json`): at 1.1.0 it cannot touch the M8 manifest. A schema 1 manifest is
checked with the tool of its own commit (`7d3639c` for 1.0.0-rc.1).

## 5. Verify the candidate independently

Requirements: git and Python 3.11 or later (standard library only) for the manifest; for the
rest, the toolchain of section 5.3.

### 5.1 The manifest

```bash
git clone https://github.com/arthur-fay/demand-forecasting-model.git atlas && cd atlas
git checkout <candidate commit>
python3 docs/release/rc_manifest.py --check
```

Exit 0 prints `OK: the checkout matches docs/release/atlas-1.1.0-rc.1.json` and the tree
fingerprint with the number of tracked files it covers. Compare the fingerprint with the one
published for the candidate in pull request #13 (and, after approval, in the annotation of the
`v1.1.0-rc.1` tag); it cannot be written into the repository, because every tracked file but
the manifest is part of it. Exit 1 means the checkout is not clean, the manifest is missing or
is not a JSON object, or the checkout differs from it: the tool names the paths and the files
that differ (the first 50, then the total) and the sections that differ. Exit 2 means the tool
cannot run (no git, Python older than 3.11, not the top of a checkout) or a committed record is
malformed or contradicts another (section 4). A shallow clone, or one
made with `core.autocrlf=true`, verifies like any other.

The M8 candidate verifies with its own tool, on its own tree, in a clone of its own (in a
checkout used for section 5.3, the files that the static build writes are untracked at
`7d3639c`, whose `.gitignore` predates M9, and the tool refuses the checkout):

```bash
git clone https://github.com/arthur-fay/demand-forecasting-model.git atlas-m8 && cd atlas-m8
git checkout 7d3639c && python3 docs/release/rc_manifest.py --check   # atlas-1.0.0-rc.1.json, 441 files
```

### 5.2 How the manifest was generated

The manifest is the candidate's last commit, made alone, from a clean checkout of the final
tree:

1. every other change committed; `git status` empty;
2. `python3 docs/release/rc_manifest.py --write`, then `--check` (which notes that the
   manifest is not yet committed);
3. the manifest committed alone, and pushed;
4. `--check` in a fresh clone of the pushed branch.

Any later change to the content makes `--check` fail. A change before approval, the review's
included, is made on the pull request and the manifest is regenerated last again (the candidate
is still `1.1.0-rc.1`), and the new tree fingerprint replaces the old one in the pull request; a
change after approval makes a new candidate, `1.1.0-rc.2`.

### 5.3 The generated artifacts match the sources

On the candidate commit (Linux x86-64 or aarch64, Python 3.12, uv 0.11.32, Node.js 22.22.2 or
later in the 22 line, an LF checkout), each of these regenerates a committed artifact from its
sources and must leave `git status` empty:

```bash
uv sync --locked
uv run atlas api openapi | diff - docs/api/openapi.json         # the API contract
uv run pytest tests/test_m7_fixtures.py --no-cov                # the dashboard fixtures are the API's answers
uv run atlas static verify                                      # the static export, byte for byte
uv run pytest tests/test_m8_release.py --no-cov                 # every version declaration equal
cd web && npm ci
npm run gen:api && git diff --exit-code -- src/api/openapi.gen.ts
npm run build && git diff --exit-code -- dist && npm run verify:dist
npm run build:pages && git diff --exit-code -- atlas-static-site.json && npm run verify:pages
cd .. && git status --porcelain && python3 docs/release/rc_manifest.py --check
```

The full checks, job by job, are those of [RELEASE_CANDIDATE.md](RELEASE_CANDIDATE.md)
section 3 plus M9's ([STATIC_DEMO.md](../STATIC_DEMO.md) section 8); CI runs them on every
push to the pull request (`ci.yml`, `pages.yml` part A, and `dependency-audit.yml`, which a
change to the locks triggers).

### 5.4 The research results

The research runs that involve the regression (M2, M3 and the legacy holdout) reproduce byte for

uv run python -c "import numpy"` prints the core); the M4 run also reproduced with OpenBLAS's AVX2
kernels in the M8 audit. The commands are in [DEVELOPMENT.md](../DEVELOPMENT.md), "Reproducing the

## 6. Versioning policy

Unchanged from 1.0.0 ([DEVELOPMENT.md](../DEVELOPMENT.md), "Versioning"): the code carries the
version being released, `1.1.0`, in every declaration (section 4, `versions`), and the deployment
tooling accepts `MAJOR.MINOR.PATCH` only. Candidate status lives outside the code: in this
document, in the manifest's `candidate` field and in a tag `v1.1.0-rc.1` that **only the owner
creates, after approval**. Changes the review requires before approval are made on the pull
request, with the manifest regenerated last (section 5.2). A change after approval makes
`1.1.0-rc.2`, which needs `rc_manifest.py` to take a candidate name first (it names every
candidate `rc.1`). The final release is tagged `v1.1.0` on the approved commit. The `v1.0.0-rc.1`
tag, if the owner approves it, belongs on `7d3639c`, separately from 1.1.0 and under the M8 gate's
own conditions, the NYC data terms of its condition 3 included ([RELEASE_GATE.md](RELEASE_GATE.md)
section 1; [STATIC_DEMO.md](../STATIC_DEMO.md) section 11).

## 7. Deployment, publication and rollback

- **Publication (GitHub Pages)** needs the owner's separate decisions, recorded in a separate
  reviewed pull request, and three repository settings ([STATIC_DEMO.md](../STATIC_DEMO.md)
  sections 9 to 12). This candidate changes none of them: the publication record is unchanged
  (every condition false), Pages is not enabled by it, and no workflow was dispatched.
- **Deployment (M6 phase B)** needs the owner's written authorisation
  ([VPS_PHASE_B_RUNBOOK.md](VPS_PHASE_B_RUNBOOK.md)). The runbook is unchanged; for this
  candidate its release ids and identity checks read `1.1.0` where it shows `1.0.0`.
- **Rollback** in the repository means not merging pull request #13, or reverting its merge:
  1.1.0 changes no research result, snapshot file or legacy artifact. On a server, rollback is
  as for 1.0.0 ([RELEASE_CANDIDATE.md](RELEASE_CANDIDATE.md) section 5).
